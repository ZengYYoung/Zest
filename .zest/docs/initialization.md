# 项目初始化（M115）

Web 点击“接入并初始化”后，自动建立 `.zest/`、迁入已有文档、建立源码索引并启动项目调查。
同一次操作开启当前项目的自动理解，由独立后台进程完成；完整范围仍可按需查看，不逐步拦截批准。
不需要输入“先阅读整个项目”等提示词，也不需要自行选择后台调查模块。
默认初始化是幂等的：同一项目再次接入或准备时，复用已有调查和文档，不重复调用模型。
后续版本变化应作为项目状态检查与增量维护处理，不作为重新初始化。

## 使用

更新代码后，先在原服务终端按 Ctrl+C，再在 Zest 项目根目录运行：

```bash
uv run zest web serve --port 8000
```

打开 `http://127.0.0.1:8000`：

1. 设置中填写 DeepSeek API Key。没有配置时可以先接入项目，本地资料仍会准备，页面提示补上模型配置。
2. 选择项目根目录，点击“接入并初始化”。已有登记项目在对话上方点击“初始化项目”。
3. 本机自动准备固定范围并开始调查，无需再去设置开启开关或逐条批准；缺少 API Key 时保存后继续。
4. 后台自动整理项目目标、架构、接口/流程、依赖、开发方式和设计约束。刷新或关闭页面不取消独立后台进程。
5. 完成后显示简短摘要，点击“查看项目文档”，或直接在原对话框提问。

当前调查只读取选定 Git 提交，不读取未提交改动；尚无提交时只建立本地文档目录，提示先提交源码。
初始安全摸底最多 200 个文件、4 MiB，仅提供起始线索。M130 起，新调查使用完整项目文件目录，
同一提交内按需读取其他允许源码，无需因未进入初始样本而追加授权；见 [项目范围读取](project-source-access.md)。
当前认知策略最多 32 次物理模型调用、30 分钟，包含获准的已知格式补试；真实服务用量仍可能计费。
执行上限和项目目录按轮冻结；请求分页与上下文窗口自动处理，完整读取证据留存。
页面不把“本地目录建立完成”当成“模型已经理解项目”。

## 文档与本地状态

### 固定工作流（M124）

新创建的初始化、增量与补全资料包冻结 `workflow_contract`：整理资料 → 梳理模块结构 →
调查核心流程 → 核对与局部修正 → 生成文档。模块和业务内容按项目选择，阶段与结束规则固定。
协调图没有补查循环：初次核对后最多一次定向补读，最多两个任务，然后核对并发布。
这两个任务与格式修复仍消耗原来的 32 次调用/30 分钟总预算，不另开预算。

核对结构或引用错误，最多用已有原文做一次局部重新核对（每轮调查最多一项修复请求）；
不猜测替换引用，不重新抓取项目资料。身份无法关联时也不能接收原响应，修复仍须返回精确身份。
已知提供商 JSON/Schema 格式失败沿用最多一次格式补试与完整收据；未知结果仍停止，不自动重发。
修复再失败则分类保留，其他有效结论继续处理，不为格式问题安排源码补查。

一条 observed 结论若只有部分独立属性通过，原结论与完整核对明细保留；程序可发布通过的子项，
同时完整保留其主体、属性、条件、断言和对应原文。原句不因此整体通过；推测或有未解决冲突的
结论不提取子项。之后原结论/子项出现冲突或失效，会暂停同组子项复用。
待补充区域只列剩余属性，已支持内容不再加入定向补读目标。

模型把证据缺口标为 `[补读源码]`、`[外部资料]` 或 `[分析推导]`；后两类保留解释与未知，
不自动反复读源码。缺少标记时仍保守地按证据缺口处理，标签不能让未支持内容成为事实。
源码补查优先真实矛盾与核心流程，预算不足时正常保留缺口。

`summary.readiness` 与原调查状态分离：`ready` 表示用途/架构/流程均已有自动核对内容，
可以开始使用；部分领域有内容为 `limited`；没有核对内容为 `unavailable`。
`knowledge_status` 保留有无缺口，原调查 `partial/failed` 不伪装成全部完成。
这是初始资料的可用性提示，不是完整功能覆盖率或模型准确性认证。
已结束记录可本地重新整理摘要与文档，但不会追溯执行新规则或重发历史请求。
旧批准包保留旧工作流；新创建的调查使用新规则。M130 的项目持续授权不再绑定内部工作流哈希，
但每轮调查仍冻结其具体执行契约。

M131 起，新调查在已有事实核对之后执行主题规划、逐页正文写作与整页复核，
产物仍位于 `.zest/docs/initialization/`。页面数量和主题按实际事实规划，六栏目只检查覆盖。
写作请求计入原 32 次/30 分钟总预算。人工修改保留并生成候选，单页失败独立恢复；
详见 [工程文档与页面恢复](engineering-documents.md)。旧调查不追溯触发新写作请求。

旧档案发布器仍支持以下固定页面（没有新文档契约、失败调查或无可发布事实时）：

- `index.md`：观察版本、调查状态、发现数、缺口和导航。
- `purpose.md`：项目目标、用户和功能。
- `architecture.md`：模块职责、入口及协作。
- `api.md`：有来源支持的接口及核心流程；参数、返回、鉴权等缺失信息保留待确认。
- `dependencies.md`：数据和外部依赖。
- `development.md`：启动与验证说明，区分静态命令和实际执行。
- `decisions.md`：约束、已知设计背景及待开发者补充的事项。

原文档、迁入资料和团队已有文档保留，不删除原 `docs/`，不覆盖同路径不同内容的团队文件。
写入冲突会显示“部分项目理解”，并列出冲突路径。
自动核对发现和待确认内容分别编排，附源码路径、行号、观察提交及调查身份。
文档不证明功能已合并、部署或测试通过；缺失的团队背景应向相关开发者确认。

索引、调查、checkpoint、调用收据和 `initialization.json` 位于本地私有状态目录，默认是项目的 `.zest/state/`。
初步理解通过当前版本的认知来源自动进入问答；对话自动使用已建立的同版本源码索引，
不要求先提交新生成的文档才能在本机使用。版本变化时不复用旧版本索引或把旧认知当作当前事实。
共享文档仍需开发者检查、提交和推送后由团队同步。本模块不自动提交、推送或运行项目。

## 恢复与接口

- `GET /api/projects/{project_id}/initialization`：只读当前状态、进度、版本和结果，不启动调查或写文档。
- 耐久网页操作 `initialization.prepare`：`project_id`，可选 `replace_pending`；准备资料，重复准备复用已保存身份。
- `initialization.initialize`：`project_id`，一次操作准备、启用自动批准并开始；可选 `resume_setup` 只继续缺少模型配置的初始化，不推翻用户暂缓。
- `project.import` 的 Web 主入口传 `automatic_understanding=true`；未带此标志的旧接口仍仅准备。
- `initialization.decide`：`project_id`、`approved`、`sha256`，可选 `automatic_maintenance`；批准须匹配完整冻结包和模型配置。
- `initialization.start`：仅启动原排队任务，或继续写入已有终态调查结果；不能直接重发未知模型请求。
- `initialization.recover`：核对原调用账本后继续；不确定响应仍会拒绝重放。
- `initialization.context-decide`：`project_id`、`actor`、`sequence`、`approved`、`sha256`，只决定一条已保存、尚未发送的较长请求。
- `initialization.context-decide-many`：只处理当前界面列出且哈希一致的一批扩展请求，整批校验成功后一次继续；不授权未来请求。
- 完整范围与扩展请求沿用 `/api/cognition/{run_id}/preview`、`/context-requests`。

准备前先保存预定调查 ID。准备中断后会复用原调查，而不是重新创建第二个工作流。
文档发布中断可继续本地写入，不再次调用模型。
调查结束且发布进程未运行时显示“等待整理文档”，不会持续转圈；
发布中的异常保存为可恢复的失败状态。结构化计划缺口按所属部分与问题生成可读文本。
调查核对失败时，只发布已核对结论与待确认项，显示部分完成并保留原调查失败记录；
无效引用仍不能成为已确认知识，也不会为文档整理重放模型请求。
底层保留显式人工重建的恢复能力，不在日常界面展示为常驻操作。
重建需要新的资料批准，旧调查保留；未知结果仍须先核对，不能通过重建绕过。
后台中断或请求结果不明时显示“核对并继续原初始化”；不会自动启动新的调查。
已失败调查若有完整保存的格式无效响应，会保留失败与缺口，不再派发该任务；
它不阻塞其他尚未发送请求的批准。真正的 pending/uncertain 调用或缺失响应收据仍阻止继续。
M116 已接入事件维护：打开、切换项目和任务完成时检查本地 Git，也可在项目状态中手动检查。
首次确认同时说明后续自动维护规则；有意义的新提交自动增量更新并简短汇报，复用初始化身份。
空闲时不定时扫描；完整规则与恢复边界见 [项目更新检查](maintenance.md)。任意项目自主开发仍待后续模块。

## 补全与待查分类（M121）

已建立部分理解后，可以点击“补全未完成的项目理解”或“按需补充项目知识”。Web 主入口自动准备、
批准并开始；底层准备接口仅复用原调查的固定资料清单、已读位置、旧断言、问题与失败任务目标，不执行模型。
新调查有独立身份、批准哈希、32 次调用/30 分钟上限；不重放旧请求，不改写原调查。
来源版本变化、原结论/核对记录变化、旧调用结果未知均会阻止复用，须重新核对来源。

M122 增加 **设置 → 项目理解 → 自动批准项目理解**。按项目开启一次后，当前等待中的初始化/补全
及以后发起的调查自动批准并启动，范围内的长请求也会继续，无需逐条点击。关闭后只停止新批准，
已开始的任务继续。模型配置或规则改变需重新开启；结果未知、已拒绝和已失败的任务不会自动重试。
开关不会无限发起补全任务；需要补全时仍由开发者发起，随后批准与执行自动完成。
细则见 [项目更新检查](maintenance.md)。

规划上下文只列出包内阅读缺口和候选位置；每个调查任务收到对应领域的完整旧断言、问题，
然后重新读取原文。完整冻结包仍可在范围详情查看。较长请求继续按原规则单独批准，预算不扩大。
`initialization.repair` 准备上述范围；重复点击复用当前身份，准备中断可继续。
`initialization.republish` 只把已有终态档案重新生成文档，不调用模型、检查更新或启动后台调查。

新批准包冻结逐项核对规则，每批两项。某项引用/结构错误时先按 M124 的上限局部修复，
仍未通过则保留待查；其余有效项仍可发布。缺失、重复或陌生身份的原响应不能接收。
跨结论冲突继续阻止接收；已批准旧包不改变批次身份和执行规则，不猜测或替换引用 ID。
新发现应按独立可核对的规则表达，避免多个功能塞进一条总述；连贯流程的因果关系仍保留。

文档将未完成内容分为尚未核对、核对失败、分析线索、包内待补读、包外资料、调查问题和失效历史。
未知的旧字符串不凭关键词推测成“需人工确认”。同一问题跨栏目计数一次，各相关栏目仍可查到。
尚未解决的历史事项和计划缺口保留来源，不因补全任务结束就自动关闭；相同版本、同栏目的
完全相同事实可去重，不能用文字相似判定历史问题已解决。补全后可能仍为部分理解。

## 验证记录

### 跨轮待办收敛（M126）

“调查结束”与“所有历史问题清零”分开。旧实现每轮带入全部历史问题，而补充计划只看到
最新一轮线索，导致早期待办遗留、后续新问题持续叠加；摘要还把计划缺口重复加到另一种总数上。

现将计划缺口、报告问题与候选统一为有稳定身份的当前知识队列。同版本、同断言与来源的
完全相同事项跨轮合并；措辞相似不等于同一问题。计数包含计划缺口且全局去重，卡片与文档一致。
原断言有同版本、同来源、原样通过核对的结论时可退出当前队列；原断言被原文明确反驳时
作为已否定的候选保留历史，不再要求反复核实它为真。冲突、推测与证据不足仍不成为事实。

新补充包使用 version=2：从整个历史队列选最多四项明确可定位的事项，由程序直接建立任务，
不再次调用全项目规划模型，也不为补齐六部分额外生成缺口。来源清单、选中事项、原记录哈希
与完整出处冻结在包内。任务产生的剩余问题沿用选中事项身份，不因模型换一种说法增加新待办。
一项在当前资料下尝试后仍未解决，标为已尝试，后续批次跳过；无新事项时不新建调查、不调用模型。
补充结果不会通过文字相似或“读过文件”被认定已经回答业务问题。被更正但不能证明等价解决的
旧断言也只保留已尝试状态，不强行清零。原调查、核对、调用收据均不改写。

历史分析、外部背景和没有具体位置的一般问题分别保留，不作为无边界全项目补全任务。
主界面收起这些记录；详情区显示可处理/已尝试/外部/待明确数量，仅在有新事项时显示定向处理入口。
可直接自然提问；这些记录不是需要开发者逐项批准的清单，也不代表初始化仍在后台无限运行。
旧 version=1 包继续按原冻结视图校验和恢复，展示层更新不追溯改变请求身份。
`initialization.republish` 可只重新整理已有文档与计数，不调用模型。

初始化专项使用离线模型验证准备、完整调查/自动核对、文档生成、首次自然问答、拒绝、版本变化、配置变化、
准备中断身份复用、发布恢复、文档冲突、部分理解、未知请求阻止重发、只读状态、缺少模型、空仓库、重复接入、
后台启动和真实独立子进程完成。并行调查线程也验证继承本机模型配置，避免线程中回退到其他 `.env`。
浏览器使用隔离的临时加法项目和独立离线后台进程验证接入、范围卡片、页面刷新、完成摘要和生成文档。
截图与摘要位于忽略目录 `work/web-smoke-m115/`。
这些是流程和来源约束验证，不代表真实模型的项目理解质量已验收；本轮没有真实模型调用。
