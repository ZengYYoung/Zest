# 项目更新检查（M116）

自动检查仅由三个事件触发：打开项目、切换项目、Zest 完成对话任务。
首次初始化完成后也会检查一次。右上角 **项目状态 → 检查更新** 可随时手动检查。
空闲、窗口重新获得焦点、打开设置或输入消息均不触发周期性 Git 扫描。

手动检查在项目状态窗口的按钮下方立即显示等待反馈；返回后保留检查时间和结果。
没有新提交时只说明本地版本检查已完成，不把未完成文档或沿用事实说成重新核验；
另有未提交改动时单独提示，不能冒充已同步理解。
发现变更时概述相对本轮检查开始时项目理解版本的新增、修改、删除和类型变化文件数量，
列出最多三条近期 Git 提交说明，并可展开最多三十个安全文件路径。提交说明是开发者的 Git 记录，
不是独立语义核对结论；摘要只在本地读取提交元数据，不增加模型调用。
检查完成与后台增量理解进度分开显示，等待批准、部分完成、失败或中断都有对应提示。
概述保存在私有 maintenance.json 的 last_check.summary 中，进度读取不重新扫描 Git；
后续无变化的检查生成新的空变更回执，不沿用上一轮文件清单。

已结束的历史更新不在每次打开项目时重新占据主对话；新完成的汇报以简短摘要显示，详情折叠。
关闭提示不删除状态记录，项目状态窗口仍可查看。知识缺口不等于正在等待人工核对的任务。
若调查因完整请求超过上限而在零次模型调用时停止，状态显示 blocked 和真实原因，保留旧认知版本。
提供“重新准备本次更新”显式操作：保留旧调查与尝试记录，为当前版本建立新的固定增量包。
普通检查不重建这类失败尝试，结果未知或已有调用的其他状态不能通过该入口重放。

新增量包以 model_view_version=1 固定模型视图方式：规划阶段文档和目录各最多 8000 字符，
历史线索最多 6000 字符；任务内只携带对应路径的线索，最多 4000 字符。完整历史清单和原包仍保留，
每次调用前继续校验原基线和完整清单；省略的线索有覆盖数量，不代表已解决。旧包不改变请求视图。
原文证据不截断为不完整结论，48000 字符上限和原调用预算不变；不能保证所有大型项目都无需另行拆分。

检查读取本地 Git；不自动 fetch、pull、合并、提交或推送。其他成员的改动需先由开发者同步到本地，
才会进入检查范围。未提交改动只显示为工作区状态，不自动改写共享认知。

## 自动维护

在 **项目状态 → 检查更新** 发现变更后，按显示的状态继续：

- 提示“模型或自动维护范围已变化，请重新确认”时，点击同一窗口里的 **确认并开始更新**。
  此操作按当前模型重新开启当前项目的自动理解，立即检查并启动已有变更，不需要再去设置。
  它通过现有 `understanding.configure` 持久操作记录完成，而不是只写旧版维护开关。
- 等待本轮批准时，可在此处查看冻结资料，再点击 **允许本轮更新**；补充范围审批也在此处完成。
- 中断或结果待核对时，使用 **核对并继续原更新**；发送前因资料过多停止时，使用 **重新准备本次更新**。
- 进入排队、分析、核对或发布后，窗口持续显示后台进度。完成后查看下方文档；部分完成会保留原因及恢复入口。

对话更新提示复用同一组操作入口。提交操作失败时，错误直接显示在项目状态窗口内。
重新确认会授权后续事件触发的自动理解；可在设置关闭。它不重放未知请求，也不等于已经完成调查。

更新活动期间显示旋转指示、流动等待动画、当前阶段和持续计时，并列出实际模型调用数、调查完成数及已发布页数。
计时优先采用原调查开始时间，旧记录没有时间时从本次查看开始；“最近读取”表示网页收到进度回执的时间，
不表示模型刚产生新结论。阶段提示不是完成比例，不显示估算百分比。文档账本进入写作后显示更新文档阶段。
完成、部分完成、失败和等待确认时停止动画，并显示各自结果；系统减少动态效果设置下保留静态状态提示。
进度连接失败时停止运行指示，明确后台可能仍在执行；只对已观察到的活动任务每 5 秒重试读取进度，
正常活动任务每 2 秒读取。恢复后清除错误；终态停止活动轮询。读取重试不检查 Git、不创建更新、不重发模型请求。

M135 起，页面恢复按实际原因区分。原调查用完调用数或时间预算后，“继续原任务”不能重置预算，
不会再用相同按钮循环排队。窗口显示具体原因；没有页面计划时显示“尚未生成页面计划”，不显示“已发布 0 / 0”。
这时可以明确点击 **基于已有事实开始新一轮文档生成**：新建独立身份和最多 32 次调用/30 分钟预算，
仅规划、撰写及复核文档，沿用原调查核对事实与固定版本，不重新调查，不增加旧任务预算或覆盖其调用记录。
此操作可能产生新的模型调用，需要用户点击新入口；不会因普通检查或读取状态自动开始。
已经完成的页面及保存的正文复核尽量复用；已知结构或语义失败可在新轮次重新生成。
未知结果不能通过新轮次重发；待调查事实、资料缺口和人工冲突需核对对应原因，不能靠重复续写消除。
修改了后端代码的已有本机服务需重启并刷新页面，才能提供新恢复命令。

M136 修正新轮次沿用旧失败计划容量的问题，并对新布局文档提供同一预算内的有界修订与独立复核。
如果正文全部完成，但原文档目录有人工作修改，窗口显示 **本轮文档已生成，原目录已保留**，
并提供 **查看本轮新文档目录**。此时 `已发布 5 / 5` 表示本轮五页正文均已保存；
维护整体仍可因保留原目录而为 partial，不需要再次生成正文。新目录候选不会自动覆盖人工目录。
具体恢复与发布约束见 [工程文档与页面恢复](engineering-documents.md)。

在 **设置 → 项目理解 → 自动批准项目理解** 开启一次，对当前项目保存授权。
初始化、补全、增量调查自动推进；M130 新调查按项目目录自主补读并组织上下文窗口，
不再因单次请求超过内部默认长度而追加审批。旧任务仍按其原有身份处理。
关闭后不批准新请求，已开始的任务继续。M123 的 Web“接入并初始化”和“初始化项目”主入口
在点击说明中明确启用当前项目的自动理解，用户无需另去设置；底层单独 decide 接口仍可仅批准一轮。
检查本身不调用模型；发现有意义的新提交且已启用维护时，后台准备并调查增量资料，
完成后简短汇报，更新 `.zest/docs/` 中对应文档和同版本源码索引。

每轮限安全、已提交项目资料，模型调用最多 32 次、30 分钟。摸底 200 文件、4 MiB 只限制起始采样，
新调查的读取范围是固定 commit 的完整允许目录。请求在发送前按实际长度自动组织，
仍保留授权、来源及完整请求哈希，单请求不超过 48000 字符。参见 [项目范围读取](project-source-access.md)。
新的持续授权不绑定内部 Prompt 或密钥版本；模型目标、资料访问权限或项目位置变化时重新确认。
旧版授权保持原范围，不追溯扩大旧任务权限。

## 幂等与恢复

- 初始化身份不变；后续维护有独立调查记录。
- 同一版本的重复事件复用原更新，返回已知版本时复用已保存认知，不重新调查。
- 记录尚在执行或调用结果不明时，保留原身份，不因手动检查而重新发送模型请求。
- “核对并继续原更新”检查原调用账本；未知结果仍禁止重放。文档发布可复用终态调查。
- 自己生成文档的提交按内容哈希识别，避免更新循环；人工修改共享文档仍参与增量调查。
- 人工编辑过的目标文档保留原文并报告冲突，不静默覆盖。

M131 起，新调查增量完成后接入主题规划、正文写作与整页复核，复用原调用账本及总预算。
单页未通过复核或写盘失败保留前一版，其余页面继续；可在项目状态查看页面记录，并用
`maintenance.resume` 继续原文档流程。未知请求仍不重发。详见 [工程文档与页面恢复](engineering-documents.md)。
M132 起，新契约调查接入 [稳定事实与页面增量维护](incremental-knowledge.md)，不再默认重写无关页面。
沿用页保留正文和实际核验版本，单独更新证据检查记录。清单随团队文档共享，但导入清单不授予事实或覆盖原文的权限。

提示分别显示当前提交和认知版本。生成文档的纯提交可能不需要新调查，两个版本因此可以不同；
不能将旧结论直接标成新提交事实。失败、部分结果和等待核对也不会伪报完整更新。
进度界面仅在任务活动期间读取已有任务状态，读取本身不检查 Git、不调用模型。

## 接口

| 接口或操作 | 用途 |
| --- | --- |
| `POST /api/projects/{id}/check` | `{reason: open / switch / task / manual}`，检查一次本地版本 |
| `GET /api/projects/{id}/maintenance` | 只读检查记录、认知版本及更新进度 |
| `POST /api/projects/{id}/maintenance/enable` | 确认当前模型、固定策略的事件维护权限 |
| `GET /api/projects/{id}/understanding-approval` | 只读当前项目自动批准开关、有效状态和预算 |
| `understanding.configure` | `{project_id, enabled}`，开启或关闭当前项目的自动批准 |
| `maintenance.decide` | 核对并决定本轮较大范围 |
| `maintenance.context-decide` | 决定一条尚未发送的扩展请求 |
| `maintenance.context-decide-many` | 按完整身份和哈希一次处理当前列出的一批请求，不授权未来请求 |
| `maintenance.resume` | 核对并继续原更新身份 |
| `maintenance.documents-new-round` | `{project_id, source_run_id, source_sha256}`；按原页面记录哈希明确新建仅生成文档的轮次 |
| `maintenance.reprepare` | 显式重新准备发送前因资料过多而停止、且调用数为零的增量任务；保留旧记录 |

写入接口沿用本地 Origin 校验。检查记录、授权、文件哈希与锁放在私有 `.zest/state/`，
不包含 API Key，不随团队文档共享。当前接通对话 TaskRunner 完成事件及初始化完成事件；
并非任意外部开发工具的任务监听，也不代表完整自主开发和远程团队事件订阅已经实现。

自动批准设置保存于 `understanding-approval.json`。新 v2 授权绑定项目、根目录、模型目标、资料权限版本及总预算，
不包含 API Key，也不绑定内部 Prompt 哈希。每次自动决定均保存具体调查身份及授权快照，
请求正文、来源和回执继续留存；旧 v1 授权保持其原有范围与校验。
此设置不授权代码修改、测试执行、部署、提交或推送；失败、拒绝、预算耗尽和未知结果不触发新的调查重试。
