# Zest 相近项目调研与接入体验改进

调研日期：2026-10-18。核对 GitHub 当前公开 README、工作流程，以及 RepoAgent 的 runner、
CodeBoarding 的 CLI 入口。未安装或实测第三方产品；以下区分来源声明、源码观察和 Zest 的设计建议。

## 相近项目与可借鉴部分

| 项目 | 核对到的做法 | 对 Zest 的启发 |
| --- | --- | --- |
| [DeepWiki-Open](https://github.com/AsyncFuncAI/deepwiki-open) | 主入口输入仓库，自动分析结构、生成文档与图表并组织为 Wiki；当前 README 称为 Grok-Wiki | 接入应是一项自动生成任务，用户先得到可用的项目说明和清晰进度，内部调查步骤可收起 |
| [RepoAgent](https://github.com/OpenBMB/RepoAgent) | 围绕 Python 对象做 AST 分析与引用关系整理；首次生成、检查点和后续变化更新统一在 run 流程中 | 按对象/模块保存理解状态与证据，复用已生成内容；已有理解的更新应明确落到原条目 |
| [CodeBoarding](https://github.com/CodeBoarding/CodeBoarding) | 静态符号/关系提取后由模型组织组件说明；保存 analysis.json、fingerprint.json；支持 full、incremental、partial | 先建立稳定结构底座，再逐模块调查；用指纹找受影响部分，而非每次重新理解整个仓库 |
| [Potpie](https://github.com/potpie-ai/potpie) | 当前是 CLI 优先的上下文图谱；setup 后由配置的 agent 按任务摄取/更新上下文；范围包括代码、历史、决策和团队知识 | 长期项目顾问需要代码之外的项目事实，并根据具体问题主动补充上下文；其 CLI 形态不必搬进 Zest 的 Web 主界面 |

上述 README 展示的主流程以配置、运行分析、产出结果为中心。由此得到的产品判断是：
Zest 可以把受限的只读调查作为后台作业，用户明确点击初始化后不必审批每个内部步骤。
这不是对各项目所有权限与失败处理实现的完整审计，也不代表生成结论天然准确。

## 源码观察与适用边界

- [RepoAgent runner.py](https://github.com/OpenBMB/RepoAgent/blob/main/repo_agent/runner.py)：
  首次运行进入 first_generate；对象生成成功更新状态并保存检查点；后续重建结构后载入旧文档，
  再按待处理对象调度。失败对象保留未生成状态。主要对象分析针对 Python，不能直接替代 BlindBox 的 Java/TS 分析。
  该实现也有删除再生成文档目录、暂存生成文件的行为；Zest 应继续保留人工文档，不自动修改 Git 暂存区。
- [CodeBoarding CLI](https://github.com/CodeBoarding/CodeBoarding/blob/main/codeboarding_cli/main.py)：
  默认 full，另有 incremental 与 partial；认证和额度错误有可识别退出状态。
  README 明确增量需要已有基线，无基线时提示先做全量分析，而非隐式回退全量。
- [CodeBoarding 的使用与基线说明](https://github.com/CodeBoarding/CodeBoarding#common-commands)：
  架构记录带来源引用，指纹与分析文件可以纯本地保存；是否提交由团队决定。

## Zest 的推荐主流程

选择根目录 → 点击“接入并初始化” → 自动准备 .zest、收集安全资料、建立索引、规划调查、
分模块阅读核对、生成文档 → 简短完成摘要 → 直接对话。

正常路径只要求用户明确启动一次。缺少模型配置时提示填写，保存后继续；源码没有提交时提示先建立版本。
后台内部的工具调用和范围内长请求自动处理，保留原有真实进度、来源、调用账本和预算。
结果未知的调用不能通过自动化重发；读代码无法获知的实际部署、历史理由和团队约定继续保留未知。

已初始化项目再次操作要复用原身份、检查状态；更新优先按变化影响范围执行。
入口自动化与理解完整度分开验收，不能用“任务完成”代替“每个业务事实已经覆盖”。

## 本轮已落地

- 正文及输入文字改为清晰黑色；修正全局 p 样式覆盖正文颜色的层叠问题。
- Web“接入并初始化”直接准备并启用项目理解自动执行，不再要求先去设置开关再批准。
- 未初始化卡片、旧等待范围卡片、配置模型后的继续操作统一调用一次初始化入口。
- Web 发起补全也可直接继续自动执行；已结束调查仍幂等复用，未知结果不自动重试。
- 新增 initialization.initialize 命令；旧底层 prepare 仍保留“只准备、不发送”的接口语义。

## 后续优先级（设计建议，本轮未重写理解引擎）

1. 按模块建立覆盖清单：业务能力、主要入口、接口契约、关键调用、数据与外部依赖。
   当前按六部分组织文档不等于这些问题已经逐项回答。
2. 把未读源码缺口变成可执行的定向阅读任务，在预算内自动补查、核对并回写。
   补查核实后关闭对应条目；历史待查保持可追溯，但不无条件累加到每轮的当前待办。
3. 用文件/对象指纹和依赖关系更新受影响知识，区分有效、待更新和缺乏依据的内容。
4. 问答按当前知识回答，发现缺口再主动读取对应源码；界面继续保留对话、项目状态和设置。

Zest 的潜在价值在于持续维护项目事实、变更与协作背景，帮助接手和长期开发。
这需要用真实项目问题验证正确率、来源适用性、更新及时性和回答连续性；仅有自动文档生成不足以证明这些能力。
