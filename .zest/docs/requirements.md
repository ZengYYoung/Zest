# 已确认的产品要求

确认日期：2026-10-17。依据：开发者与项目所有者的产品访谈。

## 定位

Zest 是面向单一项目、长期参与的项目管理 Agent 与开发顾问。
帮助新人接手项目、团队成员理解接口与模块协作，并支持长期开发。
用户表达产品目标，Zest 负责组织调查、开发、测试和项目知识维护。

## 使用方式

- Web 是主要使用入口；当前阶段无需登录、注册或随机 Web token。
- 选择项目根目录后，目标体验是自动建立 `.zest/`、初始化项目认知。
- 初始化后可直接自然交流，无需每次要求 Agent 先通读项目或人为选取所有资料。
- 主界面以连续对话为中心，另有设置和项目状态入口；项目状态可查看文档。
- 打开项目时，目标是检查 Git 变化、维护相关项目知识，以简短小弹窗汇报。
- 后台模块与工作流复杂度不直接映射为主界面的多个导航入口。

## 需求与开发

- 模糊需求需要结合项目知识反复提问，确认产品目标、业务规则和完成标准后行动。
- 遇到影响业务行为的新歧义应回来询问开发者，不自行决定关键业务规则。
- 明确后的任务应连续完成理解、开发、测试，并持续更新项目状况。
- 最终交付本地改动、测试结果及遗留问题，供开发者检查。
- 提交、推送需开发者明确要求；不能把完成开发解释为自动合并或部署。

## 项目文档与团队协作

- Zest 仅维护 `.zest/docs/` 内的项目文档，包括需求、API、架构、设计理由及开发说明。
- 既有 README、docs 等资料可读取并迁入；此后不同时维护原位置的第二套文档。
- 原 docs 可保留为历史资料，或在迁移核对后作为可审阅改动删除。
- 团队项目文档随 Git 提交；个人对话、偏好、缓存、数据库与运行记录留在本地。
- 其他使用者在内容推送远程并同步后获知更新，不要求实时共享未提交的本地讨论。
- 同一分支、同一版本的文档保持一致；不同开发分支可有不同状态和约定。
- 回答接口问题时说明用途、用法及可证实的分支、合并、部署状态；缺少依据则说明未知。
- 既有项目缺少设计理由时，应指出缺口并建议联系对应团队，不能凭代码编造历史动机。

首次外发需确认固定资料范围，完成后自然问答自动使用同版本初步认知与索引。

空闲时不定时扫描，也不自动拉取远程。自主开发完整流程仍待后续模块；真实模型语义效果仍需单独实测。
