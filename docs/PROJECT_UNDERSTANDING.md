# Zest 的长期项目认知方向

- 日期：2026-10-14
- 状态：产品要求、首轮项目认知档案、后台调查协作及按任务创建子 Agent 已确认；具体工作流、记忆结构与技术实现待逐项设计。
- 历史恢复已完成；以下认知建设体系尚未实现。

## 1. 已确认的产品要求

Zest 是长期参与一个项目的管理员 Agent，目标覆盖理解、开发、诊断、修复与更新。它应主动建立并持续维护项目认知，而不是把寻找文件和整理上下文的工作交给用户。

开发模式从需求讨论、方案决策、实施和验证中持续积累文档、项目知识及任务经验。导入模式即使面对没有原作者介绍、文档不足的项目，也应通过设计好的 Skill、工具和工作流自主调查，形成后续维护所需的认知基础。

用户可选择介绍项目、提供文档或指定资料。这些是补充和纠正入口，不是开始工作的前提；新人不必先知道应该阅读哪些文件。交互式选源不再作为项目理解的主路径或默认下一模块。

“理解整个项目”要求覆盖与具体工作相关的业务、架构和实现，并随着变化持续核对。不能把一次扫描、模型自述或文档生成等同于完整理解；Zest 应能说明已掌握内容、依据及未弄清的部分，并主动继续调查。

### 1.1 已确认：首轮交付项目认知档案

导入项目后的第一轮自主调查，应形成一份持续维护的“项目认知档案”，供新人阅读，并作为 Agent 后续开发、修复与继续调查的导航。用户于 2026-10-14 明确同意以下六部分及认知来源规则。

| 部分 | 应回答的问题 |
| --- | --- |
| 项目目标与业务边界 | 解决什么问题？有哪些用户、功能及业务规则？ |
| 模块与架构关系 | 各模块负责什么？入口在哪里？如何协作？ |
| 核心业务流程 | 关键操作经过哪些接口、函数和数据处理步骤？ |
| 数据与外部依赖 | 使用哪些数据库、外部服务？关键数据如何流转？ |
| 开发与验证方式 | 如何配置、启动、测试？哪些步骤已有实际验证？ |
| 约束与认知缺口 | 有哪些设计约束、文档矛盾、待核实内容及后续调查任务？ |

每条认知保留来源、观察版本，区分已查证事实、推测和未知。关键流程说明应关联具体代码位置及版本；只从配置或文档获知的运行方法，不能写成已经运行验证。

用户没有提供介绍时，Zest 自主调查并整理；用户补充背景后，核对并更新相关认知。缺失背景可以形成待核实问题和后续调查任务，不应编造答案来填满六个部分。

后续接到开发/维护需求时，Agent 利用档案定位相关流程、约束和测试，并继续读取必要代码。档案的保存格式、检索方式、更新机制、专业 Agent 分工及具体调查验收规则尚未确定；本次确认的是交付目标，不代表自主调查已经实现。

## 2. 需要分别设计的核心部件

下面是讨论框架，尚未确定具体存储、角色数量或实现顺序。

| 部件 | 在项目维护中的用途 |
| --- | --- |
| 项目认知总览 | 组织目标、业务边界、模块职责、主要流程、开发/测试方式，作为调查导航 |
| 可追溯知识与文档 | 保存需求、设计理由、约束、接口说明和维护经验，关联证据与适用版本 |
| 检索索引与代码工具 | 按任务主动定位和读取相关代码、文档及历史；不能要求整仓库一次塞进上下文 |
| 主题/任务记忆 | 留存某个领域的调查进展、已排除假设、决策及未完成事项，支持再次接手 |
| 认知建设 Skill 与工作流 | 引导 Agent 如何调查、核对、整理产物和补缺，提供阶段反馈与完成标准 |
| 持续更新机制 | 在开发、修复和版本变化后更新相关认知，识别过时或矛盾的记录 |

多个专业 Agent 可以承担不同领域，但它们的记忆需要共享项目与版本身份、保留依据，不能各自留下互不相容的“事实”。已确认按具体任务创建子 Agent；专业能力如何配置、主题空间和知识复用方式仍待确认。

Skill 描述工作方法；LangGraph 管理流程状态、暂停与恢复；检索、记忆及工具提供资料。Skill 文本不能代替程序中的权限、预算和版本检查。

## 3. 导入后的自主认知建设：待细化的流程草案

1. 接入固定项目版本，询问是否有可选介绍或文档；没有也可以继续。
2. 在允许范围内自主调查项目结构、依赖、入口、业务模块、测试与已有文档。
3. 针对重要流程进一步读取关联代码和历史，整理事实、推测、矛盾和缺口。
4. 形成带证据的认知总览、文档/知识草稿、检索材料与后续调查任务。
5. 向用户展示调查覆盖与仍需帮助的问题，进入持续开发和维护；以后随版本增量更新。

这不是已经存在的执行链。首轮档案的六部分与来源规则已确认；首批支持语言、调查预算、具体数据结构、自动采纳与人工确认规则，以及模型数据授权范围都待共同确定。自主生成产物不意味着所有内容都要用户手写或逐段整理。

本地读取和模型外发是不同动作；未来可以讨论一次明确批准一个有边界的调查工作流，避免让用户每读一个文件都决定一次，但不能把先前某个问答请求的批准当作整项目外发授权。

### 3.1 已确认：主会话协调，子 Agent 后台调查

用户提出在摸底与制定计划之后，将深入调查分派给后台子 Agent，保持主会话可交互，并于 2026-10-14 确认以下协作边界：

- 主 Agent 保留初步项目地图、调查计划和任务进度，负责与用户沟通、协调调查与核对返回成果。
- 子 Agent 根据计划开展深入调查，逐步返回发现、证据及缺口；主 Agent 可根据新信息追加调查或调整任务重点。
- 后台调查期间，主会话可以继续讨论和推进已有充分依据的工作，不必等待整个项目的全部调查完成。
- 涉及尚未查清部分的具体修改，应查询并等待相关调查结果；等待范围与该项工作相关，而不是冻结整个主会话。
- 返回成果经核对后逐步更新项目认知档案；摸底形成的初步认知仍须区分事实、推测和未知。

这是协作方式的确认，不代表后台执行已实现。现有单次协作问答仍在返回前等待汇总，尚无独立后台任务派发、阶段成果接收或交互协调机制。

子 Agent 按任务创建的组织方式见 3.2；主题记忆、任务通信、后台执行与恢复方式、并发和预算继续逐项确认。本次规则不代替已有模型数据、具体修改、验证和源码选择的独立批准。

### 3.2 已确认：按具体任务创建子 Agent

用户选择“按任务创建”：主 Agent 根据调查计划和具体目标派发子 Agent，例如“调查支付回调的幂等处理”。角色随当前任务安排，不预先要求每个模块拥有固定负责人身份。

任务完成后结束本轮执行，调查成果与任务记录仍然保留。长期项目认知的积累应独立于某个执行实例，不能因为执行结束就丢失已保存的依据与发现。后续任务如何检索和利用这些积累，作为下一项设计单独确认。

这项选择不确定具体并发数量、模型/工具配置、记录保存格式或异常后的恢复方式，也不表示后台执行已实现。暂停、失败或尚未完成的调查不能被写成已完成成果。

## 4. 当前能力与缺口

目前已有固定版本原文、词法检索索引、Python 声明地图、已确认知识、只读 MCP、受控协作问答，以及隔离候选修改/验证/管理源码回退。它们是构建项目管理员的基础工具。

当前 `project import` 只完成登记，不会自动运行完整认知建设；终端新问题仍用默认来源及可选相对路径，没有自主调查循环。现有协作 Agent 使用预先批准的有限上下文，尚无独立主题记忆体系、主动项目文档生成或完整的认知更新工作流。

历史恢复只恢复原任务及其批准/结果；它不等于长期记忆，不会自动把旧回答加入新请求，也不会在未知执行状态下自动续跑。

下一次只敲定一个设计点：**新建的子 Agent 如何利用以前任务积累的认知？** 具体保存格式、检索实现及后台执行方式继续分别讨论。
