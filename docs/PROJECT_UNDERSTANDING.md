# Zest 的长期项目认知方向

- 日期：2026-10-14
- 状态：产品要求已确认；认知建设工作流、记忆结构与技术实现待逐项设计。
- 本次先实现终端历史恢复，不同时实现下述整个体系。

## 1. 已确认的产品要求

Zest 是长期参与一个项目的管理员 Agent，目标覆盖理解、开发、诊断、修复与更新。它应主动建立并持续维护项目认知，而不是把寻找文件和整理上下文的工作交给用户。

开发模式从需求讨论、方案决策、实施和验证中持续积累文档、项目知识及任务经验。导入模式即使面对没有原作者介绍、文档不足的项目，也应通过设计好的 Skill、工具和工作流自主调查，形成后续维护所需的认知基础。

用户可选择介绍项目、提供文档或指定资料。这些是补充和纠正入口，不是开始工作的前提；新人不必先知道应该阅读哪些文件。交互式选源不再作为项目理解的主路径或默认下一模块。

“理解整个项目”要求覆盖与具体工作相关的业务、架构和实现，并随着变化持续核对。不能把一次扫描、模型自述或文档生成等同于完整理解；Zest 应能说明已掌握内容、依据及未弄清的部分，并主动继续调查。

## 2. 需要分别设计的核心部件

下面是讨论框架，尚未确定具体存储、角色数量或实现顺序。

| 部件 | 在项目维护中的用途 |
| --- | --- |
| 项目认知总览 | 组织目标、业务边界、模块职责、主要流程、开发/测试方式，作为调查导航 |
| 可追溯知识与文档 | 保存需求、设计理由、约束、接口说明和维护经验，关联证据与适用版本 |
| 检索索引与代码工具 | 按任务主动定位和读取相关代码、文档及历史；不能要求整仓库一次塞进上下文 |
| 主题/任务记忆 | 留存某个领域的调查进展、已排除假设、决策及未完成事项，支持再次接手 |
| 认知建设 Skill 与工作流 | 引导 Agent 如何调查、核对、整理产物和补缺，提供阶段反馈与完成标准 |
| 持续更新机制 | 在开发、修复和版本变化后更新相关认知，识别过时或矛盾的记录 |

多个专业 Agent 可以承担不同领域，但它们的记忆需要共享项目与版本身份、保留依据，不能各自留下互不相容的“事实”。是否采用多个常驻角色、按任务派生角色或主题空间，后续单独确认。

Skill 描述工作方法；LangGraph 管理流程状态、暂停与恢复；检索、记忆及工具提供资料。Skill 文本不能代替程序中的权限、预算和版本检查。

## 3. 导入后的自主认知建设：待细化的流程草案

1. 接入固定项目版本，询问是否有可选介绍或文档；没有也可以继续。
2. 在允许范围内自主调查项目结构、依赖、入口、业务模块、测试与已有文档。
3. 针对重要流程进一步读取关联代码和历史，整理事实、推测、矛盾和缺口。
4. 形成带证据的认知总览、文档/知识草稿、检索材料与后续调查任务。
5. 向用户展示调查覆盖与仍需帮助的问题，进入持续开发和维护；以后随版本增量更新。

这不是已经存在的执行链。首批支持语言、调查预算、产物结构、自动采纳与人工确认规则，以及模型数据授权范围都待共同确定。自主生成产物不意味着所有内容都要用户手写或逐段整理。

本地读取和模型外发是不同动作；未来可以讨论一次明确批准一个有边界的调查工作流，避免让用户每读一个文件都决定一次，但不能把先前某个问答请求的批准当作整项目外发授权。

## 4. 当前能力与缺口

目前已有固定版本原文、词法检索索引、Python 声明地图、已确认知识、只读 MCP、受控协作问答，以及隔离候选修改/验证/管理源码回退。它们是构建项目管理员的基础工具。

当前 `project import` 只完成登记，不会自动运行完整认知建设；终端新问题仍用默认来源及可选相对路径，没有自主调查循环。现有协作 Agent 使用预先批准的有限上下文，尚无独立主题记忆体系、主动项目文档生成或完整的认知更新工作流。

历史恢复只恢复原任务及其批准/结果；它不等于长期记忆，不会自动把旧回答加入新请求，也不会在未知执行状态下自动续跑。

下一次认知设计先只敲定一个问题：**导入项目后，第一轮自主调查应交付什么样的“项目认知总览”？** 然后再决定工作流、检索和主题记忆如何支撑它。
