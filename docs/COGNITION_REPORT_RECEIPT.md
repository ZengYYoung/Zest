# 报告逐条接收与空文件观察

日期：2026-10-15；模块：M042。修正首轮调查中“一条无效引用导致整份报告丢失候选”的交付问题；不增加模型调用、修改或执行权限。

## 为什么会引用空文件

M041 的 T1 确实读到了固定版本的零字节 src/__init__.py。工具 read 成功，协调器给所有成功读取分配 R 编号，模型因此在一条推测中引用 R2 说明文件为空。报告接收器随后禁止空正文引用，整个报告被拒绝。

读取文件成功、存在正文证据、语义支持结论是三个不同判断。零字节文件不是读取故障；“该文件为空”属于文件元数据观察，不能沿用要求非空原文的正文引用协议。

## 空读取的处理

- read 保留固定 commit、路径、blob/hash、行段及原始读取结果。没有正文时附 observation：empty_file 表示整个文件为零字节；empty_text_window 表示本次窗口没有正文，但文件本身可能还有内容。file_size_bytes 与 more_after 分别说明文件大小和续读情况。
- 两类观察标明 can_cite_as_text=false，协调器不分配 citation_id，不放入 R 正文证据表。模型视图仍可见元数据，重复观察仅在视图去重，持久工具动作不删。
- 现阶段元数据观察保留在任务过程，不直接进入自动核对事实/共享知识。结论仍须引用实际 read 得到的非空正文；证据不足保留未知。没有新增元数据事实发布通道，也不补写文件内容。

## 逐条接收的边界

原生模型输出继续统一经 with_structured_output 和有字段描述的 Pydantic 类型。缺字段、错误类型或不可解析的完整响应仍按原规则拒绝；没有补默认字段、修 JSON 或重发请求。本模块不修复 M041 的 T3 缺 scope_requests 或 T2 未知请求。

完整报告通过类型与报告级校验后，本地逐条校验发现的文本、类别、引用集合、唯一性和非空正文。有问题的候选进入 report_validation.rejected_findings，记录原始索引、字段路径、错误码与原因；其他候选进入原文语义核对，不能直接成为共享知识。

report_validation.original_report 保存原报告，原生响应收据保持原样；accepted_indices 保留原始位置。第一条无效、第二条可接收时，后者仍叫 T1:F2，不改名为 T1:F1。该记录是程序生成的接收审计，不是新增模型输出。

有候选被隔离时，任务强制 partial；全部无效时保留零发现与明确接收缺口。报告级字段/列表预算错误仍整体失败，敏感输出不进入隔离正文。核对、补查和总调用预算沿原约定，没有为了修复报告额外调用模型。

M044 将 findings 的“最多六条”改为约六条的软建议：不再按发现条数整体拒收，也不剪裁超出部分；每条仍需独立引用校验和语义核对。既有完整响应 32000 字符防线显式纳入 POLICY.max_response_chars，规划/调查输出 4096、保留报告输出 8192 token 与总调用预算继续执行。unknowns/scope_requests 的原约定、本地字段与敏感内容边界保持原样。

接收结果与原报告进入任务 checkpoint。响应已保存而发布中断时，可以在原授权与恢复规则允许下复用 checkpoint；没有响应、无效或未知调用仍不自动重发。旧真实 run 因指令/schema 变化不能直接恢复到本实现。

CLI、终端、六部分档案与只读 Web 显示“候选未接收”及原因。隔离候选不进入待语义核对发现表，也不进入共享知识；完整原报告仍可在任务接收记录和逐次响应中审阅。旧结果缺少 report_validation 时照常只读展示。

## 验证与原成绩

M041 保存的 T1 原报告纯本地回放：六条中五条通过本地业务形状/引用校验，一条空引用隔离，状态 partial。T3 原始缺字段响应继续被 Pydantic 拒绝。没有调用模型、语义补核、发布到旧知识库或修改原质量分；“五条可继续核对”不等于“五条真实认知通过”。

离线测试覆盖空文件与空窗口区分、接收隔离、全拒收、原报告保留、原始编号、敏感数据边界、实际 MCP 读取到独立核对的链路，以及发布中断后的 checkpoint 复用无新请求。前端覆盖拒收原因的只读展示。新的线上效果需要重新审阅完整包并明确批准。

随后按用户明确的一次真实测试指令执行 M043：正常报告接收实际运行，但任务空读取和候选隔离均未触发；另有八条报告被报告级六条上限整体拒收。因此目标分支的线上效果仍未知，原离线结论与历史真实分数保持原样，见 [本次覆盖记录](COGNITION_ACCEPTANCE_M042.md)。

M044 对该原始八条报告回放：八条均可进入逐条核对，报告原文、引用与编号保持不变；M041 的空引用仍被单独隔离、缺必填字段仍被拒绝。这里仅验证本地接收，不补做语义核对或改写旧成绩。新增“八条有效候选加一条坏引用”经真实 MCP/任务图进入独立核对的离线回归，防止数量放宽绕过逐条边界。

下一步定向真实验收使用固定空文件/两段非空原文，通过生产任务图和真实 MCP 生成输入，前三轮决策明确来自本地夹具；仅最后一条报告请求使用真实模型，要求八至十条独立候选。原始响应不修改地保存；另建明确标注的合成坏引用负例离线检查隔离，不冒充模型原输出、不增加外发。它是组件验收，不重新计算整个项目的质量分，完整具体预览在本模块提交后冻结、另行批准。

上述定向方案随后独立冻结并获用户批准，M045 实际执行一条请求：模型原样返回 10 条候选，全部通过引用接收，空文件只在 unknowns 中作为元数据说明；派生的本地合成第 11 条坏引用单独隔离、原 10 条与编号保留。限定的组件检查通过；没有追加语义核对或发布知识，完整冷启动质量分保持原样。另发现包内未读资料误列 scope_requests 的质量问题，详见 [定向真实验收](COGNITION_ACCEPTANCE_M044.md)。

M046 将模型报告的自由文本 scope_requests 替换为具名 material_requests，程序按固定目录派生包内/包外待办，需求错误独立留痕，有效发现继续核对；原报告/响应不变，旧自由文本不迁移。报告收束保留完整批准目录并单列读取来源，分类规则与离线验证见 [资料需求分类](COGNITION_MATERIAL_REQUESTS.md)。这不补做 M045 的真实请求，也不扩大其批准。
