## 1. 本轮要回答的问题

现有固定版本静态调查能否自主找到关键资料，形成对新人接手有用、可核对的六部分档案？先评价当前实现，再根据具体失败证据选择一个小修正模块。不预先改变 Agent 组织、检索后端、预算或持久化结构。

工程闭环与认知质量分别记录。离线测试证明编排、协议与恢复的部分行为；真实试跑检验具体样本上的模型表现。两者都不证明完整理解、生产运行状态或所有项目上的可靠性。`partial` 可以包含有价值的结果，`completed` 也可能存在语义错误。

## 3. 样本与人工参考答案

初始建议是一个用户熟悉的小型真实 Python Git 项目；用户随后选择从 GitHub 寻找公开项目，并确定个人收支 CLI 样本，见 [M035 样本准备](COGNITION_SAMPLE.md)。继续采用一个固定 commit、一种模型、一次冷启动调查的候选方案；实际模型及外发仍需确认。Zest 自身可以作为后续对照，但不能仅用自我描述丰富的仓库判断通用效果。

选样时检查：有真实业务用途和至少一条跨模块流程；代码、文档、依赖声明可人工核对；规模可在现有包预算内审阅；能够区分已实现行为、文档目标和静态资料无法证明的事项。没有天然文档矛盾就记为未覆盖，不人为改写真实样本制造结果。

人工在模型运行前编写并冻结参考答案，建议包括：

- 约 10 条关键事实，覆盖六部分，注明原文路径、物理行号、完整 commit、文件 SHA-256 和重要性。每条只描述一个可判断的事实。
- 1 条真实跨模块核心流程，拆成约 4—6 个关键步骤与关系；每步保留原文依据，静态调用线索不冒充运行轨迹。
- 约 3 项静态资料无法确认的事项，例如实际部署状态、真实外部服务配置、未记录的历史选择理由。注明为什么证据不足；项目没有这些信息不算缺陷。

答案与评分记录放在**被调查仓库之外的独立本地目录**，不纳入源码、知识库、用户介绍或授权包；即使文件被 Git 忽略，也要检查批准包内没有这些内容。模板不含实际答案。当前开发仓库可以保存通用方案，实际样本的答案、全文包和请求账本默认私有，不提交 Git。

参考答案不限定模型只能发现这 10 条。新增真实发现也逐条评分。事后发现参考答案错误时保留修订前版本、修订原因与证据，不为了迎合模型改答案。样本选定后冻结样本身份、参考答案文件哈希和评价规则。

## 4. 评价规则

人工评价者直接核对固定 commit 原文，不以核对 Agent 的意见作为答案；有争议的条目标记待人工裁定。先审阅原始结论，再记录程序核对状态。复合结论拆成原子判断，所有子判断仍关联原 finding ID；等价重复结论合并统计，并保留全部来源 ID，避免补查重复抬高分数。

| 维度 | 记录方式 |
| --- | --- |
| 事实与证据 | 对每个 observed 原子结论分别记录：事实正确/错误/无法确认，引用完整支持/部分支持/不支持/无法核对；正确且完整支持才算可信 |
| 关键覆盖 | 预先冻结的 N 条事实，逐条记正确覆盖/部分覆盖/遗漏/错误；严格覆盖为正确且证据完整的条数/N |
| 核心流程 | 按预先冻结的步骤及关系逐项核对，不只看函数名是否出现；记录正确条数/总条数及具体断点 |
| 未知与推测 | 逐项检查预设未知是否明确保留、是否被猜成事实；推测独立列出，不混入事实正确率 |
| 自动核对误收 | 在 auto_reviewed 的 observed 原子结论中，统计事实错误、无法确认或未被完整引用支持者；同时列出重要误收实例 |
| 自主查找 | 记录任务起始线索与实际读取路径；查找线索外的文件是行为证据，不能单独作为质量通过条件 |
| 资源与失败 | 请求数按规划/调查/核对及 completed/invalid/uncertain/pending 分组；记录总耗时、partial/failed 原因、预算中断、重复读取和原文截断 |

事实可信率 = 正确且完整支持的唯一 observed 原子结论数 / 全部唯一 observed 原子结论数。自动核对误收率 = 不可信的唯一 auto_reviewed observed 原子结论数 / 全部唯一 auto_reviewed observed 原子结论数。分母为 0 时记 N/A，不能报 100% 正确或 0% 误收；无法裁定的条目单列，不从分母静默删除。

准备阶段不预设一个总分掩盖重大问题。建议将“关键事实错误进入共享认知”及“将无法证明的运行/设计背景写成已核对事实”作为优先修正信号；具体通过门槛随样本共同确认并在调用前冻结。只有一个样本一次运行时报告实例和计数，不宣称稳定性或总体准确率。

工程边界单独验收：包外来源不得读取；调查不得修改/执行项目或发布；未知请求不得重发。准备阶段和未来试跑分别记录零调用与实际调用证据，不用终止状态代替账本。真实试跑不额外制造硬杀/重试场景；异常恢复先利用既有离线证据，真实异常出现时才检查。

## 5. 执行前检查与后续步骤

以下是未来操作手册，本模块未对真实样本执行这些步骤。现有 CLI 支持这些入口，无需新增 eval 服务或自动评分模型。

### 5.1 本地准备，仍不调用模型

1. 共同确认样本、完整 commit、模型 provider/name/base_url，以及是否接受现有固定预算。当前 POLICY 是固定契约，并非 CLI 可调整参数：32 请求、初始 4/合计 6 任务、最多 2 并行、每任务 4 轮、1800 秒软时间预算、单响应最多 4096 tokens。若需要更低程序预算，先单独设计小改动，不手改已生成的包。
2. 在仓库外创建全新私有状态目录和评估目录。冷启动状态不导入历史共享认知，也不人工确认业务答案；记录被管理仓库 HEAD、工作区状态及 Zest 执行版本。
3. 使用 doctor 检查本地依赖与配置，只记录就绪状态，不回显 `.env`。配置有效不证明连通性；连通性请求也属于外发，需明确授权。
4. 登记项目并用完整 commit 构建摸底，再从该 survey 创建认知包。参考命令如下，尖括号均为待填参数：

```bash
zest --state-dir <仓库外的新状态目录> doctor
zest --state-dir <仓库外的新状态目录> project import <样本仓库绝对路径>
zest --state-dir <仓库外的新状态目录> survey build <project-id> --commit <完整commit> --format text
zest --state-dir <仓库外的新状态目录> cognition create <project-id> --survey-id <survey-id>
zest --state-dir <仓库外的新状态目录> cognition preview <run-id>
```

5. 将完整 preview 私有保存，检查 commit、全文与哈希、模型目标、工作指令、预算、跳过原因；按事实/流程统计哪些参考证据实际入包，人工答案本身不得入包。确认 shared_knowledge 为空；否则不是冷启动，需重做准备。当前 create 要求本地模型配置，但不会调用模型。
6. 冻结参考答案与通过规则，填写模板“执行前身份与许可”。重要事实证据未入包时先记录采集缺口，与用户决定是否换样本；不能事后删掉遗漏项来提高覆盖率。

### 5.2 明确批准后，才能真实执行

开发会话需要用户针对**本次具体 run、完整资料包、模型目标、指令和预算**明确允许外发，然后才能执行产品的带哈希 approve。批准准备 M034 不等于批准此步骤；不继承旧请求或旧包批准。

届时使用现有 `cognition approve <run-id> --approval-sha256 <当前预览哈希>` 启动。另用 `watch` 查看真实阶段，用 `show --calls` 保存完整结果及账本，用 `dossier --format text` 保存可读档案，所有命令继续指向同一状态目录。关闭界面不取消 worker；`--no-start` 仅入队，不能作为强制暂停保证。

输出 partial/failed 时仍保存记录并评价已有结论。出现 pending_execution 或 pending/uncertain 请求时停止追加模型操作，核对已保存记录；不自动 recover，不自动重建新 run 重发。recover 可能继续执行剩余模型节点，使用前核对已保存响应与剩余授权；扩包、改模型、改指令/预算或重复运行均需新的明确许可。

### 5.3 人工评分与最小后续修正

先保留原始结果再评分，不为了评分修改 findings、知识状态或样本。记录准备范围遗漏与包内调查遗漏两类原因；报告整个样本的关键覆盖，也单列包内可回答部分，不能只报后者。

产出：一份填完的私有记录、逐条结论/覆盖核对表、原始档案与账本、至多三个按影响排序的问题。每个问题关联具体 task/call/finding、原文证据和可能失败阶段；区分“已有证据的原因”与“尚待验证的解释”。下一模块再共同选择一个问题修正；不在验收过程中悄悄调 Prompt 或预算后只报告最好结果。
