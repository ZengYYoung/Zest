# Zest 首轮调查计划：内容契约

- 日期：2026-10-14
- 状态：用户授权整块实现，规划器已按本契约实现；人工示例仍不是模型调查结果。
- 输入基础：[M030 本地摸底记录](SURVEY.md)。
- 目标：主 Agent 根据摸底材料形成初步认知，将深入调查组织为可派发、可核对的任务。

## 1. 建议的计划成果

调查计划由三部分组成，并关联项目 ID、摸底记录 ID 和固定源码版本。

| 部分 | 内容与用途 |
| --- | --- |
| 初步项目认知 | 对项目目标、技术/模块线索的初步认识及来源；区分文档陈述、代码观察、推测和未知，帮助用户理解为何这样安排调查 |
| 调查任务清单 | 为子 Agent 提供明确目标、起始线索、预期成果和完成标准，以及优先级、依赖和调查边界 |
| 缺口与等待项 | 摸底遗漏、待核实背景、文档矛盾、暂不能调查的内容及原因；用户介绍仍为可选补充 |

首轮计划应说明六个认知档案部分分别由哪些任务覆盖，或为什么仍有缺口；不要求为每一部分固定创建一个 Agent。实际任务根据项目结构和关键流程产生，可以跨多个模块调查。

## 2. 每个调查任务应包含的信息

| 信息 | 应说明什么 |
| --- | --- |
| 任务标识与目标 | 一个可引用的任务身份，以及要解决的具体问题；避免只写“阅读后端” |
| 调查理由 | 该问题与项目理解/后续维护有什么关系，依据哪些初步发现提出 |
| 起始线索 | 摸底材料 ID、路径、符号或文档位置，关联同一版本，方便开始调查 |
| 预期成果 | 例如一条关键流程、模块职责说明、数据关系或约束清单，附证据与认知类别 |
| 完成标准 | 哪些关键问题需要回答，哪些结论需要对应原文，以及未核实内容应如何交代 |
| 优先级与依赖 | 哪些任务应先做、哪些可独立推进、哪些需要先取得另一任务的结果 |
| 调查范围与预算 | 获准的读取/检索范围与资源上限；具体策略和数值随后单独确定 |

起始线索是调查的出发点，不是用户手工指定的完整材料清单。子 Agent 可以在获准范围内继续检索和读取关联资料；发现跨范围需求时报告缺口，不能自行扩大权限。

初始任务针对调查与材料核对。项目代码执行、具体修改和验证仍适用已确认的独立授权边界；制定计划本身不等于执行这些操作。

## 3. 以 Zest 为例的任务草案

以下是说明任务内容的人工示例，不是模型已生成或已完成的调查。

**任务 T1：弄清一次问答的数据批准与执行流程。**

- 调查理由：问答是项目交互入口，需要知道数据何时准备、何时外发，以及退出/中断后怎样处理。
- 起始线索：同一摸底版本的 zest/cli.py、zest/tasks.py、zest/qa.py，以及已有问答使用说明。
- 预期成果：从提问到准备上下文、批准、模型调用、结果保存的流程说明，附关键代码位置；归入核心流程与约束部分。
- 完成标准：说明批准绑定哪些内容，哪些状态允许继续执行，哪里阻止重复批准，哪些中断情况仍然未知；每项结论有证据。
- 依赖：不必等待整个项目调查结束即可启动；其他调查任务可按实际需要利用本任务的成果。

调查过程中如果发现必须进一步理解知识来源有效性，可报告相关问题，由主 Agent 协调追加调查或调整依赖；不在初始计划中假定所有关系已知。

## 4. 任务结束与项目认知的区别

建议完成标准针对具体调查目标。子 Agent 返回的成果应能指出已回答的问题、证据、未解决事项和所受限制；到达预算或被依赖阻塞时应报告部分结果与原因，不能把目标未解决写成全部完成。

任务完成不代表相关模块已被完全理解，也不直接成为共享知识。按已确认规则，由主 Agent 协调核对，合格认知进入共享项目知识，疑点继续调查或保持待核实。

## 5. 实现入口

规划由获准工作流在后台生成，保存严格 JSON 并校验身份、来源、依赖无环和六部分覆盖/缺口。预算和工具边界见 [项目认知工作流](COGNITION.md)。本文例子用于说明字段，不冒充真实模型效果。
