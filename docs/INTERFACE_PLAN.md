## 1. 两个入口，共用一个项目状态

**已确认：Web 和 CLI 都做。** Web 负责日常阅读、调查、审阅和批准；CLI 负责终端操作、脚本集成、环境检查与故障恢复。两者操作同一份项目、任务、知识和版本记录，复用现有业务服务，不各自维护一套 Agent 或批准逻辑。

首版以单个可信本地操作者为范围：API 绑定回环地址，状态使用本地 SQLite，项目由本地 Git 根目录接入。GitHub 托管 Zest 的开发仓库；被管理项目的远程克隆、PR、多人协作、部署与数据库回退仍需单独设计。

Web 与 CLI 同时操作时，批准绑定具体记录和内容哈希，服务端重新核对状态、来源与版本。某一入口批准了当前步骤，不代表后面的模型、修改、测试或源码选择也被批准。

## 3. 前端视觉与交互方向

**已确认：以白色为主，简约、克制，去掉当前绿色主调。** 借鉴 Apple 产品的留白、清晰文字层级和轻量细节，形成 Zest 自己的项目工作台。

建议的视觉基线：

| 元素 | 建议规则 |
| --- | --- |
| 页面背景 | 白色为主，少量浅灰区分阅读区域 |
| 导航 | 白/浅灰，取消深绿侧栏；当前项以文字、细线或浅灰底区分 |
| 文字 | 近黑主文字、灰色次文字，避免浅到难以阅读 |
| 操作按钮 | 深灰主按钮、白底次按钮；一处主要动作，完整文字说明 |
| 卡片与分隔 | 少量细边框、轻阴影、适度圆角；避免每条信息都套卡片 |
| 状态 | 文案和图标共同表达；成功可用中性勾号，失败/警告少量语义色 |
| 代码与 diff | 中性阅读底色；增删颜色仅服务于 diff，保留符号和文字区分 |
| 字体与图标 | 系统字体、统一细线图标；中文可读，不依赖外部字体资源 |

视觉基线为背景 `#FFFFFF`、次背景 `#F5F5F7`、主文字 `#1D1D1F`、次文字 `#6E6E73`、浅灰分隔。当前 CSS 已按此改造；导航、按钮和成功状态保持中性配色。

桌面以项目导航与主阅读区组成；窄屏保留项目切换、主要导航、断开连接与核心操作。支持键盘、可见焦点、明确标签；状态不能只靠颜色判断。长哈希和路径可展开查看，完整内容不得只依赖鼠标悬停。

加载、空项目、无记录、来源缺失、连接断开和请求失败都需要清晰状态。每次更换项目或版本应清空旧详情、取消过期请求，避免把另一项目或版本的信息误认为当前状态。

## 4. Web 页面与功能范围

### 4.1 项目接入与概览

连接本地服务后选择已登记项目，展示开发/导入模式、管理源码版本、工作区 HEAD、未提交状态和主要声明。以后增加创建/导入向导：输入目标或本地仓库根路径，确认接入结果；项目接入本身不授予模型发送、修改或执行权限。

管理源码和工作区分别显示。用户可以查阅固定历史版本；任何“当前版本”都应明确指哪一个源码来源，不能暗示运行服务已切换。

### 4.2 源码与证据

提供相对路径/行段读取、关键词或现有索引检索、Python 声明地图。符号定位后按同一 commit 读取原文，显示实际路径、行号和哈希；超长符号分段读取，不超过已有单次读取限制。

地图首版只理解 Python 的静态声明。页面保留已解析数量、跳过原因和预算提示，不能把部分分析描述成全项目理解。自动构建/更新索引属于单独的本地操作，不在普通读取时悄悄进行。

### 4.3 调查与建议任务

建议把“调查问题”和“提出具体修改”作为两个明确的任务入口。调查输入问题与来源选择；修改建议输入目标以及允许的既有文件、新路径或精确行段。用户无需在产品界面填写 LangGraph 节点或底层协议参数。

准备阶段只在本地形成预览。预览必须完整展示问题、将发送的来源、版本、已确认知识、模型/接口、调用上限和批准哈希。用户明确批准这份请求后才调用模型；更换目标或范围须重新准备，不能继承旧批准。

结果分别展示结论/建议、引用、未知项和状态。调用失败、中断或结果未核对时保留记录，不自动重试可能已经计费的请求。协作 Agent 的分析可以展开，但不能成为没有原文支持的新事实来源。

### 4.4 候选修改审阅

每份具体修改展示基础版本、受影响文件、原文/新文哈希、diff、完整候选正文和方案哈希。用户对这份修改单独批准后才创建候选提交；拒绝也是明确记录。

待创建路径与已有代码证据区分，片段修改展示实际完整结果。候选就绪并不等于验证通过或已选择使用；原工作区和 main 保留，不能用一个按钮同时批准模型、修改、测试和源码选择。

### 4.5 测试验证

准备页显示候选来源、已安装的固定镜像、固定测试命令、文件清单、时限与隔离策略。用户批准后才运行；首版不提供任意命令输入、联网安装依赖或自动拉取镜像。

结果分别展示基线与候选的测试数量、退出码、隔离核对、容器清理、OOM、日志截断及保存日志。基线不适用时明确显示“未运行”；离线夹具、未知后端或缺失指标不能展示成正式测试成功。通过表示这套测试通过，不能保证所有需求正确。

### 4.6 管理源码历史与回退

准备选择时核对真实验证证据，并展示以前/目标版本和独立批准身份。回退必须明确目标及来源操作；中断时提供核对状态，不能直接重复执行。

页面始终使用“管理源码选择/回退”的准确措辞。现阶段不包含运行进程、流量、数据库回退或零停机发布。导出展示来源和文件清单的一致性结果，不把本地校验当作新的测试或签名。

### 4.7 项目知识与维护记录

展示目标、约束、设计决策、历史案例及其草稿/确认/失效状态、观察版本和适用范围。以后支持新建知识、明确确认和带原因失效；草稿不进入 Agent 上下文，历史信息不自动成为当前版本事实。

维护案例关联原任务、具体修改、验证和源码选择。用户确认的是可追溯记录，模型推测的根因与建议说明仍须单独审阅。活动时间线可在此基础上串起已有事件；不引入没有业务必要性的消息队列。

## 5. CLI 功能与完善方向

**已确认：交互式终端工作台，以对话和真实阶段时间线为主，第一小模块做问答闭环。** 选择项目→输入问题→完整来源预览→单独批准模型请求→真实阶段/耗时反馈→带引用的结果。项目和历史任务作为辅助入口，已有子命令继续服务脚本。修复/测试/源码选择的终端交互随后逐项设计；不在第一模块一起展开。

M028 已实现这个问答闭环，入口为 `zest ui`，当前历史恢复仍使用原任务子命令。实际使用、线程/退出限制和验证范围见 [终端工作台](TERMINAL_WORKSPACE.md)。

以下命令组已存在，继续保留。完整参数以 `--help` 和 [本地验收](LOCAL_ACCEPTANCE.md) 为准。

| 命令组 | 职责 |
| --- | --- |
| `doctor` / `web serve` / `mcp serve` | 环境检查、本地 API 与单项目只读工具服务 |
| `project init/import/list/show/overview` | 接入与登记状态 |
| `project read/search/map/ask` / `index build/search` | 固定版本证据、静态声明与现有检索 |
| `task create/list/show/approve/reject` | 持久化调查与模型数据批准 |
| `repair suggest/create/list/show/approve/reject` | 明确范围的建议、具体方案与候选创建 |
| `verification create/list/show/approve/reject` | 验证计划、独立批准与结果 |
| `release promote/rollback/list/show/active/approve/reject/recover` | 管理源码选择、回退及中断核对 |
| `release export/verify-export/capture` | 固定源码导出、清单核对与案例草稿 |
| `knowledge add/list/show/confirm/invalidate` | 项目长期知识的审核生命周期 |

后续完善重点：保留现有 JSON 输出兼容性，增加可选的简洁人类阅读格式；列表显示用途、状态和短 ID，详情保留完整身份。常见失败给出稳定错误码、原因及适用的下一步，不输出密钥或原始敏感异常。

所有入口继续支持明确 `--state-dir`；操作完成后给出记录 ID 和下一步所需的哈希。批准必须带当前预览哈希，不增加跳过所有批准的快捷参数。没有现场终端交互时，也能先 show 再明确 approve，方便可审核的脚本调用。

大批记录的项目内分页、按状态筛选、可读输出格式尚未实现，后续与 Web 使用同一查询规则；不把目前全局最近 100 项筛选当成完整历史。

## 6. 从只读 Web 到可操作 Web

当前 GET 接口继续使用现有服务。未来按一项操作一个小模块增加写入接口，依次复用本地准备、明确拒绝、带哈希批准等能力；不在浏览器复制 Git 或容器逻辑，不把任意仓库路径或 shell 命令作为通用执行接口。

新增写入接口需要同时补齐：独立本地认证、限定 Host/Origin、明确的方法和输入约束、记录与项目关联、当前状态/哈希核对、重复提交处理和可审阅事件。重复点击的 UI 禁用只是交互处理；持久化唯一请求身份与服务端约束才负责防止重复创建/执行。

模型数据批准、具体修改批准、验证批准和源码选择批准都保持独立。模型密钥留在服务端本地配置；Web 使用独立 token，当前只保存在页面内存。token、凭据和项目正文不进入访问日志、浏览器持久存储或外部遥测。

模型执行或 Git/容器操作中断时，界面报告未知/待核对状态，不通过重试按钮伪造安全恢复。多人登录、RBAC、对公网服务与生产审计不在本地 MVP 中顺带实现。

## 7. 恢复开发后的顺序

以下是建议顺序，每一步继续单独提交、记录验证和开发日志；不一次性展开全部功能。

1. **白色视觉改造与当前页面验收**：去除绿色，统一导航/文字/按钮/状态；完成源码地图页浏览器联调及窄屏、键盘检查。
2. **项目接入双入口体验**：创建/导入向导和接入反馈，CLI 保持兼容并补充可读提示。
3. **调查创建与数据预览**：Web 准备本地任务并显示完整来源，先完成这一环，再实现单独的数据批准。
4. **建议与具体方案批准**：明确修改范围，复用独立候选创建规则。
5. **验证计划与批准**：展示完整执行预览和结果，不能自动跳过人工决定。
6. **源码选择、回退及知识确认**：打通可操作的本地闭环，再完善分页和历史关联。

运行服务部署、其他语言结构解析、语义 Embedding 与 GitHub PR 协作另行确认业务场景，不为了凑技术栈提前展开。

## 8. 验收与当前进度

每个新增操作应验证 Web/CLI 状态一致、项目/版本切换不串数据、预览/批准哈希相符、重复请求不重复执行、正文按文本显示，以及模型和实际副作用不会在未批准时发生。UI 使用临时夹具验证；真实模型请求须先明确数据和接口批准，不能泛用之前某一次请求的授权。

M027 已实现白色样式并补齐 M026 地图页的浏览器联调，前端 10 项测试及构建通过。M028 最新完整后端回归为 283 项，包含 4 项既有 Docker 实测，7 项新增终端测试使用明确的离线模型。

用户已恢复开发。重要选择先共同敲定，按已确认范围推进；第一版终端问答已实现，新的 Web 写入和终端维护操作尚未自动获准展开。
